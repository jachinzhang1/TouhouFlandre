# 站点开发计划

本文描述 TouhouFlandre 的长期开发边界、优先级和 Pull Request 对齐标准。它不是任务日志，也不承诺具体发布时间；实际工作以公开 Issue 和版本里程碑为准。

## 维护原则

- 游戏规则、题库和 API 契约优先保持稳定。
- 服务端是答案、反馈和多人状态的权威来源。
- 新功能应先明确用户价值、验收标准、数据边界和回滚方式。
- 不提前建设缺乏明确需求的账号、组织空间、多租户或多实例能力。
- 涉及第三方素材、东方设定或个人数据的改动必须先说明来源、授权和隐私影响。

## PR 前置要求

提交 PR 前，开发者必须先在 Issue 中对齐以下内容之一：

- 需求背景和用户场景。
- Bug 复现步骤和期望行为。
- 题库或素材的数据来源。
- 技术方案、契约变化和验收标准。
- 与本文计划的对应关系。

未事先在 Issue 中对齐，或明显偏离本站开发计划的 PR 将被直接关闭。维护者可以要求贡献者先补充 Issue、缩小范围或拆分 PR。

## 当前维护重点

| 方向 | 目标 |
|---|---|
| 玩法稳定性 | 保持每日题、随机题、多人房间、分享和会话恢复的行为稳定。 |
| 题库质量 | 完善来源记录、字段一致性、头像映射和纠错流程。 |
| 本地统计 | 保持统计口径透明，不上传玩家历史记录。 |
| 可访问性 | 保证主要流程可键盘操作，状态表达不只依赖颜色。 |
| 部署可靠性 | 完善健康检查、备份、日志和故障排查文档。 |
| 工程质量 | 保持契约生成物、Go 测试、Vitest 和 OpenAPI 检查可重复运行。 |

## 可接受的扩展方向

这些方向可以提出 Issue 讨论，但仍需明确范围和验收标准：

- 题库扩充、字段来源补全和翻译修正。
- 新的公开反馈字段或字段比较规则。
- 单人或多人体验改进。
- 公告、友链、素材鸣谢和站点信息维护。
- 本地统计图表和导入导出体验优化。
- 生产部署、备份、监控和安全加固。
- 账号、跨设备统计、排行榜和管理后台。

账号、排行榜和后台属于较大范围能力，不能在未完成需求对齐、数据模型、权限边界和隐私说明前直接提交实现 PR。

## 不接受的 PR

- 未关联 Issue，或 Issue 未对齐需求与验收标准。
- 明显偏离本文计划，且未提前获得维护者认可。
- 大范围重构但没有行为收益、迁移方案或测试覆盖。
- 手工编辑生成物。
- 引入来源不明、授权不清或不允许再分发的素材。
- 将隐藏答案、guest token、房间号或对手昵称写入分享文本、本地统计导出或日志。
- 在前端重新实现权威答案选择或反馈比较。
- 把本地运行产物、缓存、数据库文件、日志或依赖目录纳入提交。

## 需求对齐模板

Issue 建议包含：

```markdown
## 背景

## 目标

## 非目标

## 验收标准

## 数据/素材来源

## 影响范围

## 测试计划
```

题库与素材 Issue 还应列出来源链接、授权条款和争议点。API 或数据库变更 Issue 还应说明契约变化、迁移方式和兼容策略。

## 决策记录

重大决策应沉淀为长期有效文档，而不是散落在任务评论中。建议放入对应主题文档：

- 玩法和反馈规则：`docs/gameplay.md`
- 用户功能和页面：`docs/features.md`
- 数据和素材：`docs/data-guidelines.md`
- 架构和契约：`docs/architecture.md`
- 部署和运维：`docs/deployment.md`
- 多人房间：`docs/multiplayer.md`
