# 本地统计系统

> 状态：待实施  
> 基线：2026-08-07 当前分支  
> 范围：单人每日/随机 + 多人房间对战  
> 原则：统计数据仅保存在浏览器，不新增服务端统计表、云存档或排行榜

## 一、统计口径

| 指标 | 单人 | 多人 |
|---|---|---|
| 一次游玩 | 一个结束的 session | 一个结束的 match，BO3/BO5 不按 round 重复计数 |
| 成功 | session `won` | match `win` |
| 作品统计单位 | 一个 session | 一个 round |
| 获胜猜测次数 | 获胜 session 的猜测数 | 获胜 round 中自己的猜测数 |
| 整局耗时 | session 前台有效游戏时间 | round 前台有效游戏时间 |
| 记录详情 | 一组猜测头像 | match 概要 + 展开的各 round 猜测头像 |

总胜率计算为已知结果中的 `win / (win + loss + draw)`；主动放弃、重开弃局和断线判负进入失败分母。无法在服务器保留期内恢复终态的多人草稿标记为“未完整同步”，单独提示，不参与胜率和作品统计。

作品组合图以题局为单位：灰柱为该作品答案出现次数，主题色柱为本地玩家获胜次数，折线为胜率。Tooltip 固定展示“总游戏次数、成功次数、胜率”。

## 二、本地数据模型

使用 Dexie + IndexedDB，建立三个 store：

- `records`：完成的单人 session 或多人 match，内嵌题局和猜测快照。
- `drafts`：进行中的单人 session、多人的 match/round 以及有效计时状态。
- `metadata`：schema 版本、`clearedAt`、导入迁移信息。

统一记录采用 `SingleStatsRecord | MultiplayerStatsRecord` 判别联合。多人记录包含赛制、最终比分、结束原因、各 round 结果；题局保存答案角色、作品 ID/标题/`THxx`、自己的猜测头像序列和耗时。

记录主键由来源 ID 哈希生成：

- 单人：`sessionId`
- 多人：`roomId + matchIndex + memberSlot`

不保存 guest token、房间号和对手昵称；导出文件不包含进行中草稿。所有角色与作品均保存当时快照，避免题库更新破坏历史数据。

## 三、契约补充

当前多人 `round.ended` 的答案只有 ID、名称和头像，[multi.ts](D:/MyCode/TouhouFriberg/packages/shared/src/multi.ts:84) 无法提供稳定作品 ID。需要：

1. 在 `contracts/ws/protocol.yaml` 的答案载荷增加 `workId`、`workTitle`。
2. 同步 Go `AnswerView`、投影逻辑、共享 TS 类型、协议有效/无效示例。
3. 保持数据库事件仍只存 `answerId`，由绑定题库快照在投影时水合，不修改多人数据表。
4. 允许状态为 `left` 的成员令牌在保留期内只读最终 snapshot；猜测、再战等写操作继续拒绝。
5. 离房成功后先拉取一次终态 snapshot、完成本地统计，再清理房间凭据和跳转。
6. 断线判负后再次访问时先恢复终态统计；超过服务端保留期则保留为未完整同步草稿。

单人 HTTP 契约无需修改。

## 四、计时规则

实现统一的前台有效计时器。只有页面可见且单人 session 或多人 round 处于 `playing` 时累计；多人倒计时、局间间歇、后台停留和设备休眠均不计时。

猜测耗时在用户提交动作发生时截点，不包含 API 往返时间。多人 match 总耗时保存为所有 round 有效时间之和；直方图展示可跨模式比较的题局耗时，而游玩记录仍展示完整 match 总耗时。

## 六、界面结构

页面依次为全局筛选栏、KPI 区、作品柱线图、猜测次数图、同排双耗时直方图、每日连胜区和游玩记录。桌面端双直方图同排，`max-[900px]` 以下纵向排列；作品较多时使用 ECharts DataZoom 和横向浏览。

作品图使用次数左轴和 `0–100%` 胜率右轴，柱子与折线节点共用 axis Tooltip。图例、数值和线型共同表达，不只依赖颜色。

每日题当前/最长连胜始终按全部每日历史计算，不受多人模式和时间范围筛选影响，并在组件上明确标注“历史累计”。
